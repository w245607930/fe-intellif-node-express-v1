# 技术规划解读

> 解读基线：项目根目录下的《Node.js + Express 企业级后端项目技术规划文档》  
> 解读日期：2026-08-13

## 1. 一句话定位

建设一套以 JavaScript、Express、MySQL、Prisma 和 Redis 为核心的企业级模块化单体后端模板，使后续业务只需新增业务模块，而无需重复搭建鉴权、权限、日志、校验、队列、测试和部署等基础设施。

## 2. 核心目标

规划文档包含三层目标：

1. **可运行**：具备明确的启动入口、环境配置、数据库连接和健康检查。
2. **可开发**：建立模块边界、参数校验、统一响应、异常处理、日志和 API 文档规范。
3. **可生产部署**：具备认证授权、缓存与队列、自动化测试、安全基线、PM2 和 Nginx 运维方案。

最终交付物不是某个具体业务系统，而是可复用的后端基础模板和一套统一开发规范。

## 3. 已明确的技术边界

### 3.1 第一版采用

- Node.js + Express + JavaScript。
- MySQL 8.x + Prisma。
- Redis + ioredis。
- JWT Access Token + Refresh Token。
- Zod、Pino、Swagger/OpenAPI。
- BullMQ、node-cron。
- Vitest、Supertest。
- ESLint、Prettier、Husky、lint-staged、Commitlint。
- PM2 + Nginx。

### 3.2 第一版明确不采用

- TypeScript、Docker、Kubernetes、微服务。
- RabbitMQ、Kafka、MongoDB、Elasticsearch、GraphQL。

这些约束用于控制初版复杂度。后续若要引入，应通过架构决策记录说明收益、成本、迁移路径与回退方案。

## 4. 架构判断

### 4.1 架构形态

项目适合采用**模块化单体 + 独立 Worker 进程**：

- API 进程负责同步 HTTP 请求。
- Worker 进程负责异步和耗时任务。
- MySQL 保存核心业务事实。
- Redis 提供短期状态、缓存、限流、锁及 BullMQ 基础设施。
- Nginx 和 PM2 属于生产运行层，不侵入业务模块。

### 4.2 分层原则

建议固定调用方向：

```text
Route → Middleware → Controller → Service → Prisma/Redis/Queue
```

- Controller 只处理协议适配，不直接访问数据库。
- Service 承载业务规则和事务边界。
- Schema 校验所有外部输入。
- Middleware 处理跨模块关注点，不承载具体业务。
- 公共基础设施通过集中配置或服务封装，避免模块自行创建连接。

## 5. 原规划中的关键缺口

原文技术方向完整，但仍需在实施前或实施中补齐以下可执行定义：

| 缺口 | 影响 | 处理阶段 |
|---|---|---|
| Node.js 与包管理器版本未锁定 | 开发和 CI 行为可能不一致 | 阶段 0 |
| ESM/CommonJS 未决 | 影响所有模块、配置和测试写法 | 阶段 0 |
| API 版本前缀未确定 | 路由和文档可能反复调整 | 阶段 1 |
| 错误码命名与分段规则未定义 | 客户端难以稳定处理错误 | 阶段 1 |
| Refresh Token 轮换、撤销和多端策略未定义 | 可能产生安全与体验问题 | 阶段 4 |
| RBAC 权限缓存与失效策略未定义 | 权限变更可能无法及时生效 | 阶段 5 |
| Redis Key 命名、TTL、序列化规范不完整 | 易产生冲突和长期脏数据 | 阶段 3 |
| 分布式锁安全语义未定义 | 可能误解锁或重复执行 | 阶段 3 |
| BullMQ 幂等、死信和可观测性未定义 | 任务可能重复或静默失败 | 阶段 7 |
| 数据库种子、测试隔离和清理方式未定义 | 集成测试不可重复 | 阶段 2、8 |
| 健康检查和优雅停机未明确 | 发布期间可能丢请求或任务 | 阶段 1、9 |
| 配置校验和密钥轮换未定义 | 错误配置可能延迟到运行期暴露 | 阶段 0、9 |
| 备份恢复、发布回滚未定义 | 生产故障恢复能力不足 | 阶段 9 |

## 6. 实施顺序调整

原规划将统一异常、响应、日志、校验等放在“工程化”阶段。实际实施中，这些能力决定后续模块写法，应前置为基础骨架，避免认证与权限模块二次返工。

推荐顺序：

1. 项目基线与决策冻结。
2. HTTP 基础骨架与工程规范。
3. 数据库与基础模型。
4. Redis 基础设施。
5. 用户认证。
6. RBAC。
7. API 文档和可观测性完善。
8. 队列与调度。
9. 测试门禁。
10. 生产部署与验收。

## 7. 第一版完成定义

第一版只有同时满足以下条件才算完成：

- 新环境可按文档完成安装、配置、迁移和启动。
- 用户可注册、登录、刷新令牌、退出并读取自身信息。
- 管理员可管理用户、角色、权限及其关联关系。
- 受保护接口同时执行身份认证和权限检查。
- 所有外部输入经过校验，所有响应和错误使用统一格式。
- 日志可通过 Request ID 关联一次请求，敏感字段不落日志。
- 至少存在一个可验证重试与失败处理的 BullMQ 示例任务。
- Swagger 文档与实际接口一致。
- 核心 Service 单元测试和核心 API 集成测试通过。
- PM2、Nginx、HTTPS、优雅停机、发布和回滚流程有可执行文档。
- 不提交密钥、运行日志或本地环境文件。

## 8. 当前结论

技术路线适合建设通用中小型企业后端基座，复杂度受控，扩展方向清晰。当前不应直接一次性堆叠全部组件，而应以“每阶段均可运行、可测试、可验收”为原则推进。详细任务、依赖和验收门禁见《实施路线图》。
